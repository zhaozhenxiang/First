## 目标

在 `M2-A` 和 `M2-B` 已固定 Web 主链路、输入与身份边界之后，再补齐 `ORM` 与常用数据访问体验，让模型、查询和持久化成为稳定的数据层能力，而不是夹杂在 runtime 整理过程中的返工点。

这一阶段要解决的是“数据对象如何创建、查询如何执行、结果如何回到上层链路”，而不是一开始就铺开整个工程化数据生态。

## 为什么最后做

`ORM` 放在 `M2` 最后，不是因为它不重要，而是因为它最容易把前面还没稳定的运行时假设固化进 API。

原因是：

- `Auth`、`Validation` 和异常输出已经在前两段明确了它们和请求链路的连接点
- 数据层一旦过早展开，模型、查询和持久化 API 会被迫兼容尚未稳定的上层行为
- 先稳定上层边界，再接入 `ORM`，可以避免查询、模型和错误语义反复返工

## 范围

### In Scope

- `ORM` 的模型创建、hydration、持久化、刷新和删除生命周期
- 常用查询构建、结果返回和基础读写体验
- 模型 / query builder 与容器、异常、响应边界的衔接
- 上层链路消费模型数据时的最小稳定语义
- 用测试固定数据访问主链路

### Out of Scope

- 不在这一阶段铺开完整高级关系矩阵、观察者、事件、工厂、seed、复杂分页和性能优化体系
- 不在这一阶段先做完整 migration / schema toolchain 规划
- 不在这一阶段把 cache、queue、event 等工程化能力混进数据层收口
- 不在这一阶段为了贴近 Laravel 而先做大范围 facade 或 manager 抽象
- 不在这一阶段重写前两段已经固定的 Web、输入或身份链路

## 数据访问主链路

这一阶段完成后，数据访问主链路应能稳定描述为：

1. 模型或 query builder 从统一的数据访问入口创建。
2. 查询条件、查找语义和结果集获取规则可以稳定描述，不依赖隐藏副作用。
3. 查询结果被明确地 hydration 成模型或数据对象，而不是散落的数组拼装。
4. 持久化、刷新和删除通过稳定生命周期完成，并保留一致的状态变化语义。
5. 数据层异常在边界内保持明确，在进入 HTTP / Console 输出前由上层统一处理。
6. `Auth`、`Validation`、Route binding 等上层能力可以消费同一套稳定的数据访问语义。

## 设计原则

### 1. 先把生命周期做稳，再补便利 API

优先固定模型创建、查询、hydration 和持久化边界，而不是先追求大量链式语法糖。

### 2. 查询路径和模型路径要共享同一套核心语义

能通过一个统一数据访问内核解释的行为，不额外复制一套近似但不一致的路径。

### 3. 数据层不直接承担 Web 输出责任

`ORM` 可以定义自己的异常和状态变化，但最终如何转成 HTTP / Console 输出，应由上层统一处理。

### 4. 上层能力消费 `ORM`，不反向改写前两段边界

`Auth`、`Validation`、Route binding 可以依赖 `ORM`，但 `ORM` 不应倒逼前两段重新开旁路。

### 5. 测试要覆盖查询与持久化两侧

不仅要测查得到，还要测写得回、状态变更清楚、失败路径明确。

## 交付物

`M2-C` 完成时，建议至少交付：

1. 一条稳定的模型创建、查询、hydration 和持久化主链路。
2. 一套常用数据访问体验的最小能力集。
3. 一套与上层异常 / 响应体系衔接清楚的数据层边界。
4. 一套能被 `Auth`、`Validation`、Route binding 等上层能力复用的数据访问语义。
5. 一组能证明上述生命周期成立的回归测试。

## 验收标准

`M2-C` 结束时，应至少满足：

1. 常用查询、单条查找和基础写入操作拥有一致的数据访问语义。
2. 模型 hydration、持久化、刷新和删除具有可描述且稳定的生命周期。
3. 数据层失败不会直接泄漏为杂乱的输出路径，而是能与上层统一异常出口对接。
4. 上层能力可以复用 `ORM` 的最小稳定语义，而不需要各自维护一套数据访问旁路。
5. `M2-C` 完成后，`M2` 的 Web 状态、身份与输入、数据访问三段边界可以分别描述并独立演进。
